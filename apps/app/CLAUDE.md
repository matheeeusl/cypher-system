# @cypher/app — character sheet app

Next.js 16, App Router. Depends on `@cypher/ui` for components/tokens and (as they're built out) `@cypher/engine` for rules logic and `@cypher/content` for rules data.

## App Router conventions

- Routes live under `app/`. Default to Server Components; only add `'use client'` to a file when it needs state, effects, or browser APIs — keep client components as small/leaf as possible.
- Data mutations belong in Server Actions or Route Handlers, not client-side fetch calls to your own backend.
- `app/layout.tsx` loads the three design fonts via `next/font/google` (Space Grotesk, Inter, IBM Plex Mono) as CSS variables (`--font-display`, `--font-sans`, `--font-mono`). These feed the `--font-*` mappings in `@cypher/ui`'s `@theme` block — don't re-import fonts elsewhere or hardcode font-family values.
- `app/globals.css` should stay a thin entry point that pulls in `@cypher/ui/styles/globals.css`; put any app-only CSS in its own file rather than growing this one.

## Auth (Better Auth + Neon)

- `lib/auth.ts` is the single Better Auth instance: Postgres (Neon, `DATABASE_URL`, pooled string) via `pg`, email + password with **required email verification**, Google social login, `nextCookies()` plugin. Handler lives at `app/api/auth/[...all]/route.ts`; the browser client is `lib/auth-client.ts`.
- Emails (verification, password reset) go through Resend in `lib/email.ts`. The email language is read from the `callbackURL` inside the link Better Auth generates, so always pass `/${locale}/…` as `callbackURL`/`redirectTo` from the client. `EMAIL_FROM` must use a domain verified in Resend.
- Schema was created with `npx auth@latest migrate --config lib/auth.ts` (load `.env.local` first). Re-run it after adding plugins or user fields.
- Server-side session: `getSession()` in `lib/session.ts`. `/` (the wizard) redirects to `/{locale}/auth` when there is no session; `/{locale}/auth` redirects to `/` when there is one. Check the session on the server — don't rely on client state.
- There is no Row Level Security: ownership/authorization checks for user data must live in application code (and in the graphql-api once it stores per-user data).
- UI lives in `@cypher/ui` (`AuthForm`, `ResetPasswordForm`, `AuthCard`, `TextField`, …) and takes all text via `labels` props; copy for en/pt-br is in `lib/i18n/auth.ts`.

## Characters (saved to Neon)

- Table `character` (`db/migrations/001_character.sql`): `choices` (the wizard's `WizardChoices`, not the derived sheet — it's recomputed via graphql-api so rules fixes apply on their own), a denormalized `summary` for the list, and `content_versions` (contentVersion of the Type/Descriptor/Focus used) which drives the "Rules Update" badge. Apply migrations with `pnpm --filter @cypher/app db:migrate` (reads `.env.local`; tracked in `schema_migrations`). Add new migrations as `002_….sql`, etc.
- **Database credentials (do before publishing):** `scripts/db-migrate.mjs` only reads `DATABASE_URL` from the environment and is never served (it lives outside `app/` and `public/`), but it needs DDL rights. Today one Neon owner role is used for both migrating and running the app. For production use two roles: a migration role (used only by deploy/CI, never present on the app server) and a runtime role limited to SELECT/INSERT/UPDATE/DELETE on the tables, which goes in the app's `DATABASE_URL`. Also remember `db:migrate` targets whatever `.env.local` points at — don't keep the production URL there.
- All reads/writes go through `lib/characters.ts`, and **every query is scoped by `user_id` taken from the session** — that is the only authorization boundary (no RLS). Never pass a user id that came from the client.
- Writes are server actions in `app/[locale]/characters/actions.ts`. Their input is untrusted: `lib/characters-input.ts` re-parses the shape and `lib/prepare-character.ts` re-checks every wizard step and asks graphql-api's `validateCharacterChoices` before anything is stored. It needs graphql-api running.
- Plan limits (future free/paid tiers) belong in `lib/entitlements.ts` (`characterLimit`, currently unlimited) — `createCharacter` already enforces it.
- Architecture decision: the app owns user data (auth + characters); graphql-api stays a stateless, public rules service shared with `apps/docs`. If a second client (mobile/public API) or paid rules content ever needs the same user data, move auth + `lib/characters.ts` into the service.
- Routes: `/{locale}` (list) → `/{locale}/characters/{id}` (read-only character sheet, `lib/character-sheet.ts` derives it through graphql-api, UI is `CharacterSheet` in `@cypher/ui`) → `/{locale}/characters/{id}/edit` (the wizard on its Review step; saving returns to the sheet). "Export as PDF" is `window.print()`: `tokens.css` forces the light palette under `@media print` and the page chrome uses `print:hidden`. Known simplifications: XP is always 0 and pools show `max / max` (no in-play state yet); the sheet recomputes from graphql-api on every view (5 full queries, uncached).

## Play mode (`/{locale}/characters/{id}/play`)

- The live side of a character: Pools (spend/recover), the damage-track banner, XP log, advancement, inventory (items + real cyphers from the catalog) and notes. The sheet (`/characters/{id}`) is the read-only/printable view and now shows the live Pools and XP too.
- **Data** (migration `002_play.sql`): `character.advancement` (the purchases the engine validates), `character.pool_max` (cached derived maxima), `character_play` (`spent` points per Pool — current = max − spent, so a +4 Pool purchase raises the current value on its own — plus `inventory`; its old `notes` column is unused since migration `004`), and the append-only `character_xp_entry` ledger (entries that pay for an advancement are `locked`). All access goes through `lib/play.ts`, scoped by the session user.
- **Server actions** (`app/[locale]/characters/[id]/play/actions.ts`) re-validate every argument. `purchaseAdvancementAction` is the only place advancement is bought: it derives the current tier through graphql-api, enforces once-per-tier and the XP cost (`advancementRules` from the engine), has graphql-api validate the resulting build, then records the purchase + locked XP entry in one transaction guarded by an optimistic check on the previous purchases (a stale tab gets `conflict`, never a double charge). It returns a fresh `PlayView` so the screen updates without a page reload.
- **Purchases are tagged with the tier they lead to** (the engine's convention; see `packages/cypher-engine/CLAUDE.md`). While at tier N the app collects purchases tagged N+1 (`lib/advancement.ts`).
- **Level-up picks:** reaching a new tier owes Type abilities (`tier_choose_counts`) and, for some Foci, a Focus choice. They are stored in `character.tier_picks` (migration `003`, `lib/tier-picks.ts`) and saved by `choosePicksAction`; the engine reports what is still owed in `pendingPicks`, which `PlayView.pending` turns into `AbilityPicker` panels at the top of the Status tab. Nothing blocks buying the next tier while picks are pending. Editing a character in the wizard keeps its picks unless they become impossible (different Type/Focus, a tier-1 ability now taken twice), in which case they are cleared and asked again. The top tier (`advancementRules.maxTier`, 6) has nothing left to buy.
- **Flavors** (optional, `WizardChoices.flavorId`; content in `@cypher/content` `data/flavors/`): a flavor only **widens the pool** the Type abilities are picked from — it never changes how many are picked, and the picks stay in `tier1TypeAbilityIds` / `tier_picks.type` (so skill-grant keys stay `type:<tier>:<id>`). The selector lives at the top of the Abilities step (`tier1PickPool` in `derive.ts` merges the two lists; an ability both offer is listed once, as the Type's). Changing the flavor drops the tier-1 picks the new pool no longer offers, with their skill picks (`onSelectFlavor`). Anything that calls `buildCharacterChoicesInput` must pass `content.flavor` when `choices.flavorId` is set — it returns `null` otherwise (it can't validate); that is why `prepare-character.ts`, `loadDerived` (`bundle.flavor`) and the three server actions in `play/actions.ts` all pass it. `flavorId` is an optional key of the `choices` JSON (no SQL migration; rows and drafts saved before it parse as `null`), the flavor's `contentVersion` is stored with the others, level-up pickers (`pendingChoices` in `lib/play-view.ts`) offer the flavor's abilities of the pick's tier or lower, and the sheet labels them "Flavor". If a character's flavor is removed from the content, it derives as invalid (like a removed Focus). **The pt-BR word for "flavor" is "Traço"** (plural "Traços", masculine; confirmed 2026-10-16) — it is `terms.flavor` / `abilities.flavor` in the i18n files; the docs site has the same term in `apps/docs/src/lib/flavor-term.ts` (change both together).
- **Choice abilities** (Blessing of the Gods, Cantrips; `Ability.choice` = `{ options, count }`): picking one asks for `count` more abilities. In the wizard a picker appears under the Abilities list for each chosen one (`tier1ChoiceSlots` in `derive.ts`; answers live in `WizardChoices.abilityChoices`, keyed `type:1:<abilityId>` like skill picks) and Next waits until each is complete. At tier 2+ (or for a character saved before the picks were answered) the engine reports a `{ kind: 'option' }` pending pick: `PendingChoice` of that kind in `lib/play-view.ts` (options = the choice's, minus abilities already known), saved by `choosePicksAction` into `tier_picks.options` (`withOptionPick`; no migration, left out while empty) — all `count` at once. The picked abilities are ordinary known abilities, credited to the choice ability's source (the flavor), so the sheet needs nothing extra. `buildCharacterChoicesInput` drops tier-1 answers for choice abilities the character no longer has.
- **Improved Edge** (`Ability.edgeGrant` kind `choose_zero`; the `fixed` kind, Enhanced <Stat> Edge, needs no input): in the wizard a stat picker appears under it on the Abilities step (`tier1EdgeSlots` in `derive.ts`, which replays the engine's order — starting Edge, then Type picks, then Focus abilities — so it offers only the Edges still at 0; answers live in `WizardChoices.abilityEdgeChoices`, keyed `type:1:improved-edge`, `{}` for rows and drafts saved before it) and Next waits for it. A pick that stopped being valid (the starting Edge changed to that stat) isn't sent (`currentEdgePick`) and the step asks again. Taken at tier 2+, or owed by a character saved before this existed, it is a `{ kind: 'edge' }` pending pick: a `PendingChoice` whose options are the stats (`MIGHT`…) at 0 in the derived Edge, saved by `choosePicksAction` into `tier_picks.edges` (key -> stat; no migration, left out while empty). It is the fourth Warrior ability in list order, so e2e flows that click the first four also pick an Edge.
- **Learning cantrips for XP** (`choice.learn` on Cantrips; only characters whose flavor lists it, i.e. Modern Magic): the Status tab shows a `LearnPanel` under the Advancement panel (`PlayView.learn`, built by `learnView` / `learnableAbility` in `lib/play-view.ts`). A purchase is `learnOptionsAction`: `learn.count` options, `learn.xpCost` XP, validated by graphql-api (`learnedOptions` input), then `applyLearn` writes `tier_picks.learned` (ability id -> options in the order bought, `count` per purchase; no migration, left out while empty) and a locked XP spend entry in one transaction guarded by the previous picks. `revertLearnAction` removes one purchase by index and refunds its XP as an ordinary gain entry. It is **not** an advancement purchase: those count towards the four per tier. `picksUpToTier` keeps `learned` (it isn't tied to a tier). Known gap: if an edit in the wizard makes the learned options impossible (the flavor changed), the picks are cleared like any other but the XP they cost stays spent.
- **Flavor gained in play** (`FlavorGainPanel` in the Status tab, `PlayView.flavorGain`; the panel offers it only to a character with no flavor, hides ability exchanges the engine would refuse — only Type-offered, untrained picks with no skill grant or choice of their own, see `swappablePicks` in `lib/play-view.ts` — and warns to talk to the GM first; a "my GM granted it" checkbox makes it free; in the wizard's edit mode the flavor selector is replaced by a locked note, `Wizard`'s `gainedFlavorId`): `tier_picks.flavorGain` = `{ flavorId, swaps: [{ tier, replaces, with }], costXp }` (no migration, left out while there is none; `costXp` is 0 when a character arc granted it, so undoing refunds exactly what was paid). The flavor a character has is `flavorIdInUse(choices, tierPicks)` = `choices.flavorId ?? tierPicks.flavorGain?.flavorId`: `loadDerived`, `prepare-character.ts` and `buildCharacterChoicesInput` all use it, and the last sends `flavorGain` to graphql-api, whose engine rewrites the Type picks (the stored `tier1TypeAbilityIds` / `tier_picks.type` keep the original Type abilities). `gainFlavorAction` / `revertFlavorGainAction` (`play/actions.ts`) buy and undo it through `applyPicksPurchase` / `revertPicksPurchase` (shared with learned cantrips; a cost of 0 writes no XP entry, the ledger only holds positive amounts). One flavor per character. Undo is refused (`not_revertable`) when the engine says the build would break, e.g. a later Type pick was taken from the flavor.
- **Skill-granting abilities** (Physical Skills, Life Lessons…; `skillGrant` on `Ability`): the wizard's Abilities step shows a skill picker under each such tier-1 ability and blocks Next until it is complete (`tier1SkillGrantSlots` in `derive.ts`; picks live in `WizardChoices.abilitySkillChoices`, keyed `type:1:<abilityId>` — the engine's `skillGrantKey`, replicated in `derive.ts` because the app doesn't import the engine). A grant gained at tier 2+ (or owed by a character saved before this existed) shows up as a `kind: 'skill'` entry in `pendingPicks` → an `AbilityPicker` in play mode, saved by `choosePicksAction` into `tier_picks.skills` (key → skill ids; no migration, the field is left out while empty). `buildCharacterChoicesInput` merges both into `abilitySkillChoices` and drops tier-1 keys for abilities no longer chosen. The ability can be taken again at a later tier, each time with different skills. Grants with an `alternate` shape accept either pick count (`AbilityPicker`'s `alsoAccept`, one list for both shapes; a hint in the wizard). `allowCustom` grants add a text field (`AbilityPicker`'s `custom`, `CustomSkillInput` in the wizard): a typed skill travels as `custom:<text>` (`lib/custom-skill.ts`), is kept in `derived.skills` under that id and shown as written on the sheet. The Descriptor's "N skills of your choice" accept typed skills too (`CustomSkillInput` in `SkillsStep`), and the Skills advancement lists the character's typed skills and offers "Train “…” as a new skill" for a name that isn't listed (`ChipPicker`'s `extraOption`); `purchaseAdvancementAction` re-points a typed name to the character's existing entry ignoring case. Typed skills live inside each character (no shared library across characters). Options are filtered by the grant's `mode` and the skill's current level (`specialize` lists only trained skills).
- The Skills advancement can also train a known **attack** ability (`abilityId` target; `Ability.attack`, curated by hand in `@cypher/content`): the rulebook only lets you choose "an ability that is an attack". It sits behind its own "Train a special ability instead" list rather than among the skills, `purchaseAdvancementAction` rejects a non-attack, and a trained ability is marked "Trained" in the Skills tab and on the sheet. The engine itself still accepts any known ability (characters saved before this rule may have trained one).
- **Other Options** (`lib/advancement.ts` keys `armor`, `recovery`, `typeAbility`, `focusAbility`; `isOtherKey`): once each tier one of them takes the place of a standard step, through a fifth "Other option" row in the Advancement panel (a `ChipPicker` of the four, then a searchable list of Type + flavor abilities, or the Focus options with a "talk to your GM" warning). `purchaseAdvancementAction` refuses a second one in the same tier; the engine checks the rest. `PlayView.advancement.other` (`otherOptionsView` in `lib/play-view.ts`) lists what can be taken now: Type/flavor abilities of the current tier or lower not known yet (a `skillGrant.repeatable` one may be retaken), and the unchosen options of Focus choices already made. The bought abilities are credited "Advancement (tier N)" (`AdvancementAbilitySource`); their skill/option/Edge picks are keyed `advancement:<purchase tier>:<id>` and owed from the tier before (`gainedAt` in `lib/tier-picks.ts`), and undoing the purchase drops them (`withoutPurchasePicks`). The recovery roll (`1d6 + tier + recoveryRollBonus`) and, once bought, the armor Speed Effort cost reduction show beside Effort in the Status tab and as quick stats on the sheet. A wizard edit that makes such an ability impossible is refused, like a Skills purchase that trained one: `prepareCharacterData` flags those rule codes (`ADVANCEMENT_CONFLICTS`) and `saveCharacter` returns reason `advancement`, whose message tells the player to undo that advancement in play mode first.
- **Undoing an advancement** (XP Log tab → "Advancement history"; `revertAdvancementAction`): only the newest tier's purchases can be undone (`revertableIndexes`) — an older tier can't lose one while a later tier has some, the engine would call it incomplete. The resulting build is validated through graphql-api first; the XP it cost is refunded as an ordinary (removable) `gain` entry, not by deleting the locked spend entry; level-up picks of tiers the character no longer has are dropped (`picksUpToTier`); spent Pool points are capped at the new maximums. Guarded by an optimistic check on both `advancement` and `tier_picks` (`revertAdvancement` in `lib/play.ts`).
- **Inventory rows** open on click: a carried cypher shows its catalog effect (and effect table), loaded on demand from the cypher catalog; an item the player typed just says so. `InventoryRow.description` is optional in `@cypher/ui`.
- **Skills tab**: each skill is a button that opens its catalog description (`sheetSkills` returns `description`/`custom`); a skill the player typed has no rules text, so it just says it was created by them.
- **XP log** (`XpLog` in `@cypher/ui`) shows the newest entries first, 5 to a page (`pageSize`; the advancement history uses the same `PAGE_SIZE` and the shared `Pagination` component), and goes back to page 1 when an entry is added; the whole ledger is still loaded (capped at `LIMITS.xpEntries`).
- **Client** (`components/play/PlayScreen.tsx`): optimistic, with every server call going through one in-order queue (taps arrive faster than requests; unordered, a late spend could undo a recovery). While the queue is non-empty it shows "Syncing…" and warns on `beforeunload`; e2e tests wait for it to drain before reloading. Notes are a list of short entries, editable in place (`character_note`, migration `004`; `LIMITS.noteLength` = 500 characters, 200 per character; shown newest first, 5 to a page by `NotesLog`), added, edited and removed one at a time — there is no autosave any more. `character_play.notes` is no longer read; the migration carried each old note over as entries.
- Cypher limit comes from the engine through the API (`Type.cypherLimit`); exceeding it only warns (the GM may allow it at a cost). Inventory starts empty; starting equipment on the sheet is still the Type's descriptive placeholder list.
- XP/Pools simplifications: Pool buttons are plain spend/recover (no recovery-roll dice), and Increasing Capabilities' +4 points are split freely across the three Pools (`PoolSplitPicker`; the engine validates the sum).

## GraphQL

- `lib/graphql/client.ts` — a thin `fetch` wrapper (`gqlRequest`), not `graphql-request`. Reads the endpoint from `NEXT_PUBLIC_GRAPHQL_API_URL` (see `.env.example`), defaulting to `http://localhost:4000/graphql`.
- `lib/graphql/queries.ts` — hand-written query strings + matching TS types, one section per entity (Type/Descriptor/Focus/Skill/Ability/validateCharacterChoices). No codegen yet; keep these in sync by hand.
- `services/graphql-api` doesn't have a watch-mode dev workflow by default outside this app's needs — run it with `pnpm dev:api` from the repo root (added alongside this wizard; wraps `tsx watch`). It must be running separately from `pnpm dev:app` for the wizard to work — nothing here auto-starts it.
- `ChoiceAbility.options` in `schema.graphql` is `[[ID!]!]!` (a list of option-bundles, each a list of ability ids), not a flat `[ID!]!` — a few Foci offer a "choose either X, or both Y and Z" bundled-pair option. See `packages/content/src/schemas/focus.ts`'s comment on `tier_abilities` for the source shape.
- **Known gap, not fixed:** when a tier-1 Focus choice entry has `count > 1` (Channels Divine Blessings is the one real case — pick-2-of-13), this wizard sends all chosen ability ids to `validateCharacterChoices` correctly, but the server's `mapFocusChoiceSelections` (services/graphql-api) collapses multiple `{tier, abilityId}` pairs sharing a tier down to the last one, and `@cypher/engine`'s `resolveFocusAbilities` can only hold one selection per tier anyway. Fixing it means changing that `Record<string, string>` to `Record<string, string[]>` end to end — out of scope for this pass.

## Wizard (character builder)

- `components/wizard/Wizard.tsx` is the whole thing — one client component owning all `WizardChoices` state, per-step data fetching (fetch-on-first-visit into `components/wizard/state.ts`-shaped caches), and the debounced `validateCharacterChoices` call that drives the live pool/edge/effort preview.
- One file per step kind under `components/wizard/` (`TypeStep.tsx`, `DescriptorStep.tsx`, etc.) plus `derive.ts` for the pure logic (step validity, error messages, building the mutation input) — keep new step logic there, not inlined in `Wizard.tsx`.
- The Review step's primary action saves the character through the `saveCharacter` server action (see Characters below) and returns to `/{locale}`. `Wizard` takes optional `characterId` + `initialChoices` to edit a saved character; it then opens on the Review step.
- **i18n:** the wizard is fully bilingual. All text lives in `lib/i18n/wizard.ts` (one `WizardCopy` per locale — the type forces en and pt-br to have the same keys) and is reached from client components through `useWizardI18n()` (`components/wizard/i18n.tsx`, provided by `Wizard`). Game terms shared with the character sheet (stat names, skill levels, price tiers, clothing…) live in `lib/i18n/terms.ts` — add a term there, not in two places. Names/descriptions from graphql-api are picked with `t({ en, ptBR })`; never read `.en` directly in UI. `derive.ts`'s `stepErrorMessage` takes the copy as an argument so it stays pure. The sentence "Eu sou um(a) …" uses the glossary's "um(a)" because Descriptor/Type names carry no gender in the content.
- **Engine errors are localized from codes:** `validateCharacterChoices` returns `errors` (English) plus `issues` (`code` + `params`, same order). `WizardCopy.issue()` maps each code to a sentence; unknown codes fall back to the English message. When adding a rule error in `@cypher/engine`, give it a `CharacterRuleError` code and add the translation here.
- **Descriptor step:** the list is in the book's order (Standard first, then each genre group by `category.page`), alphabetical in the current language inside a group; genre descriptors show their category on the right (`SearchableEntityList`'s `getMeta`, which the search also matches: "cyberpunk" lists five). A Descriptor with a `poolBonusChoice` (Hideous, Sensational, Sylph, Rusted… — a union: `DescriptorPoolDivide` or `DescriptorPoolOneOf`) shows `DescriptorPoolChoicePicker` (steppers or radios); the answer is `WizardChoices.descriptorPoolChoice` (`{ allocation }` or `{ optionIndex }`, the API's `@oneOf` shape; `null` for rows and drafts saved before it, reset when the Descriptor changes) and Next waits until it is complete (`descriptorPoolChoiceComplete` in `derive.ts`, the engine's rules). `buildCharacterChoicesInput` sends it only when its kind matches the Descriptor (`currentPoolChoice`). The fixed bonuses are never sent; `descriptorPoolBonus` adds them and the choice for the Pools breakdown and the Review row. A saved Hideous character from before this derives as invalid until it is edited (the engine requires the choice).
- **Drafts:** an unsaved wizard is kept in `sessionStorage` (`lib/wizard-draft.ts`, key per character id or `new`) and restored after mount, so switching language or reloading doesn't lose progress. Saving clears it.
- `<html lang>` is set on the server by the root layout from the `x-locale` request header that `proxy.ts` sets from the URL (`LOCALE_HEADER` in `lib/i18n/auth.ts`); `components/HtmlLang.tsx` still updates it in the browser, since the root layout isn't re-rendered on client-side navigation between locales.
- **SEO:** every `/{locale}` route is `noindex` by default (`app/[locale]/layout.tsx`, which also localizes title/description from `lib/i18n/meta.ts`); only the sign-in page opts in (`app/[locale]/auth/page.tsx`: `index`, canonical without `?next=`, en/pt-BR hreflang) and is the only entry in `app/sitemap.ts`. `app/robots.ts` blocks only `/api/` — the private pages stay crawlable so crawlers can read their `noindex`. A new public page must opt in the same way. Metadata merges shallowly: a nested `openGraph` replaces the parent's whole, and a layout's `title.default` still gets the parent's template (hence `appName`, not the full title).

## Testing

- `pnpm --filter @cypher/app test:e2e` (or `pnpm -F @cypher/app test:e2e`) runs the Playwright suite in `e2e/`. `playwright.config.ts`'s `webServer` starts `next dev` for you (reusing one already running locally) — but **graphql-api must already be running separately** (`pnpm dev:api`), same as for manual testing.
- First run on a fresh machine needs browsers installed once: `npx playwright install chromium` from `apps/app/`.
- `e2e/global-setup.ts` creates a throwaway verified user (directly flips `emailVerified` in Postgres), signs in once, and saves the session to `e2e/.auth/` (gitignored); its teardown deletes the user, which cascades to their characters. `playwright.config.ts` loads `.env.local`, so `DATABASE_URL` must be set. `e2e/wizard.spec.ts` runs the full walkthrough in both `en` and `pt-br` (save → sheet → edit → list → delete) plus a test for the draft surviving a language switch; `e2e/play.spec.ts` covers play mode (pools/damage track, XP, advancement through tier 2, inventory + cypher limit, notes, pt-br). Specs share one test user, so Playwright runs with `workers: 1`.
